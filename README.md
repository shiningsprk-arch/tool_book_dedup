# 查重合并（book_dedup）

MyBooks 工具箱外置工具：找出书库里的重复书籍，逐组对照后把重复项的格式并入保留项，
并（可选）删除重复记录。

- 工具 ID：`book_dedup`
- 形态：外置工具包（`manifest.json` + `backend/` + `frontend/` + `icon.png`），用 `mytool` 打包
- CoreAPI：`1.3.0`
- 授权：BSD-2-Clause（判定思路参考 BookOrbit，**未使用其代码** —— 见 `backend/NOTICE`）

## 安装

1. 在 MyBooks 里开启开发者模式（`ENABLE_TOOLBOX_DEV_MODE`）
2. 工具箱 → 上传工具包 → 选择 `dist/book_dedup-<版本>.zip`
3. **安装/更新需要重启 MyBooks 才生效**（禁用/启用即时生效）
4. 装完如果界面看起来还是旧版，硬刷一次工具页——宿主的工具前端资源 handler 不设缓存头，
   但本工具的 `index.html` 里资源带 `?v=<revision>`，改版本时会自动换掉

## 怎么用

1. **开始查重**：默认扫描全库。相似度阈值默认 85（越高越保守），结果里会显示实际使用的值。
2. **看结果**：列表每行**直接列出成员书名**（每行最多 2 个，其余点开看全部）与作者，
   并显示证据强度（确定 / 很可能 / 存疑）、可回收空间。
3. **展开一组**：点该行——对照台**就在这一行之内展开**（不是弹窗，不会盖住列表、
   也不会重置滚动位置）。对照表只列出成员之间**有差异**的字段，相同的折叠成一句摘要；
   两份完全相同时会明说「除差异项外其余都相同」。
4. **选保留哪本**：工具按规则给推荐（元数据最全 → 格式最多 → 体积最大 → 最早入库）并
   写明理由；点对照卡上的「保留这本」可覆盖它——改选后标题会如实变成「保留这本：X · 你手动选择」，
   因为原来的推荐理由已经不对了。
5. **合并**：点「先看合并预览」（同一行内就地展开），确认后执行。预览会列出
   **会复制过去的格式**与**会被丢弃的同名格式**——同名格式不会被复制（见下），
   并且**默认不勾**「同时删除重复记录」：删除不可逆，要删得自己勾一下。
   ESC 或再点一次行头即可收起。
6. **单独删除一本**：每本书的卡片上都有「删除」键——点一下就地展开确认条（写明会连带
   删除那本书的哪些数据），确认后才真的删。删掉一本之后，该组剩下的书仍可继续合并。

## 判定规则

三档证据（界面上的筛选就是这三档）：

| 等级 | 判据 |
|---|---|
| 确定 | ISBN 相同 + 媒体家族相同（ISBN-10 会换算成 ISBN-13 再比；校验位不对的一律丢弃） |
| 很可能 | 标题相似度 ≥ 阈值 **且** 相似度 ≥ 0.95 |
| 存疑 | 标题相似度 ≥ 阈值但 < 0.95（不是重复的可能性更高） |

动手之前有两道闸：

1. **作者桶短路**：作者不同的一对根本不进入标题比较（否则 25k 本就是 3 亿次两两比较）。
   没有作者的书全落进同一个"无作者"桶，桶太大时跳过并在 `stats` 里记账。
2. **卷册序号排除**（`normalize.differs_only_by_serial`）：两侧书名**只差一个卷号/期号**
   （`德川家康（第一部）` vs `（第十二部）`、`苗疆蛊事` vs `苗疆蛊事1`、
   `The Economist [Thu, 16 Jun]` vs `[Thu, 23 Jun]`）时**不成组**。
   这类对的主书名完全相同，**任何阈值都拦不住**：真书库（24,835 本）实测，不排除它们
   会报出 1584 组，其中 1374 组（87%）是"同系列不同卷"，最多一组 19 本——
   而界面上"合并这一组"一键就会把整套书删到只剩一本。
   排除了多少对会进报告与界面（「已排除卷册序号」）。

   **仍有局限**：靠括号区分、括号里又没有序号的同系列书（如 `焚舟纪（别册）` /
   `焚舟纪（烟火）`）仍会被报出来。合并前务必看清预览里的成员列表。

中文文本的处理是本工具自己定的：

- 标题先做归一化：NFKC 折全角、去标点与空白、小写
- 相似度取「完整标题的字符 n-gram Dice 与包含度的较小值」和「剥离尾部注记后的主书名」
  两个视角的较大者——`《孙子兵法》` 与 `《孙子兵法(全本)》` 判为同一本
- n-gram 的 n 由**两侧共同**决定（取较小者）。逐串各选各的会让"中英混排"的一对落在
  不同的 n-gram 空间里，相似度恒为 0（`哈利波特 Harry Potter` vs `哈利波特` 以前就是 0）
- 中文用字符 bigram，西文用 trigram；两者都不用分词器（分词结果依赖切分一致性，
  对"同一本书的两种写法"不鲁棒）

## 写操作的安全边界

删除不可逆，所以两处写操作（合并 / 单删）共用同一套守门：

1. 只接受**分组序号 + book_id**，成员由服务端回"本次扫描的索引"核对——前端传不了任意 id
2. **动手前确认保留项现在还在书库**。报告是跨重启持久化的，可能几天前扫的；
   期间你完全可能（在工具卡片上点「打开书籍页」之后）把它删了或并了。
   保留项不在 → 拒绝并提示重新扫描，**一条记录都不删**
3. 合并**先复制、后删除**：只要有该复制的格式却没复制成功，就中止且不删源记录。
   宿主会为"来源/目标书籍不存在"抛错，这类错误以前被当成"无需合并"，于是把源记录删光、
   什么都没复制、界面还说成功（0.1.3 及以前）
4. **部分失败也会如实回报**：提示写"N 条失败"，失败明细进「本次已处理」区

## 合并与删除做了什么，以及**没做什么**

**做了**：

1. **合并**：把重复项的格式文件复制到保留项（只复制保留项缺的格式），可选删除重复记录
2. **单独删除**：每本书的卡片上都有「删除」键，可就地确认后删掉那一本（不必先合并）

**没做（重要）**：

- **同名格式不会被复制。** 两本都有 EPUB 时，合并后留下的是**保留项的那一份**，
  源书那份会被丢弃。预览里会明确列出"会被丢弃：EPUB"，但这一步是不可逆的。
- **被删掉的那本书上的用户数据不会被迁移。** 收藏 / 在读 / 阅读进度 / 时长 / 评分 /
  书评 / 标注 / 书单归属都挂在那本书的 book_id 上；**删除会连带把它们删掉，而不是搬到
  同组的其它书上**。宿主侧现在会级联清理干净（上游 issue
  [PoxenStudio/mybooks#82](https://github.com/PoxenStudio/mybooks/issues/82) 已修，
  commit `a33f0c26` 新增 `webserver/base/book_data_cascade.py`，工具箱删除与宿主删除共用
  同一份清理），所以不会像以前那样留下悬空行；但"清理干净"意味着数据**真的没了**，
  **删除前请自己确认要保留哪一本**。
  ⚠️ 该修复目前只在宿主的 `develop` 线上，`v4.3.0` / `v4.2.2` 尚未包含；在旧宿主上删除
  仍会留下悬空行（书单计数与个人统计虚高）。工具本身不再区分这两种宿主——界面文案写的是
  "会连带删除这些数据"，在两种宿主上都不算说错。
- **不勾"同时删除重复记录"时**，只做格式合并，两条记录都留着（之后可自行处理）。

### 一条别再犯的界面约束

**详情（对照台与合并预览）必须是行内抽屉，不许回到居中浮层。** 0.1.1 之前用的是
`position: fixed; inset: 0; display: flex; align-items: center` 的浮层，真机反馈
「报告总是在最中间显示、盖住列表」。现在渲染在被点那一行之内（`.bd-drawer`），
`tests/test_frontend_contract.py::test_overlays_are_gone` 会守住这一点。
另外**改保留项只许重画抽屉**（`refreshDrawer()`），调 `loadGroups()` 全量重画会把
滚动位置重置掉——同文件 `test_keeper_pick_does_not_rerender_whole_list` 守着。

### 结构

```

  write_ops.py       两处写操作（合并 / 删除）的执行与记账、守门与已处理台账

    normalize.py     ISBN 校验与 10↔13 换算、标题/作者归一化、媒体家族
    similarity.py    字符 n-gram Dice、变体判定（含尾部注记剥离）
    cluster.py       候选择配对（作者桶短路）+ 并查集分组

    diff.py          只展开有差异的字段

```

### 为什么性能上不会爆

宿主仓库自带 `tests/cases/big-metadata.db` 是 **24,835 本**，两两比较是 3 亿次。
所以候选生成走"作者桶短路"：先按归一化作者建倒排，**只在共享作者的桶内比标题**，
作者不同的一对根本不比较。单个作者桶超过上限时跳过并记账（在报告的 `stats` 里如实交代），
宁可不比也不让一次扫描把服务拖住。

实测（`scripts/smoke_offline.py --perf`，25k 本合成库、作者池 200 人）：配对 **约 1.5 秒**
（149 万次比较）。这一档刻意取了最坏分布：200 个作者摊到 25k 本上，桶非常大。

**真书库另算**：拿宿主自带的 `tests/cases/big-metadata.db`（24,835 本真书）跑完整扫描，
整趟约 **24 秒**（配对 436,243 次比较、0 个桶被跳过）。合成库那个 1.5 秒不能当成真库的预期：
配对的绝对耗时由"最大作者桶有多大"与"标题有多长"决定。
